# Просто чи ефективно? Чому не обидва: Rust з Embassy для багатозадачності у вбудованих системах 

Розробка вбудованих систем завжди пов'язана з компромісами: вартість проти продуктивності, складність проти підтримуваності тощо. У цій статті ми розглянемо баланс між простотою коду та ефективністю виконання в контексті багатозадачності. Але головне - ми розглянемо підхід, який взагалі уникає цього компромісу, надаючи вам код, який є водночас і простим, і ефективним.

## Наш навчальний приклад
Введення-виведення (input-output, I/O) - це важлива частина вбудованих систем. Часто все призначення системи полягає лише у з'єднанні джерел даних із приймачами даних з мінімальними обчисленнями між ними (або й взагалі без них) - тобто введення-виведення фактично є єдиною відповідальністю. Розглянемо простий приклад I/O, який дуже часто зустрічається у вбудованій розробці: припустимо, у нас є мікроконтролер STM32F4, і ми хочемо зчитувати дані, що надходять через UART з частотою, яку визначає відправник (наприклад, зчитування даних із датчика), агрегувати їх у структури даних в пам'яті та надсилати агреговану статистику через UART щоразу, коли статистика змінюється або з фіксованим інтервалом часу. Це доволі простий приклад, але його цілком достатньо для ілюстрації наших ідей без додавання зайвих ускладнень.

![Навчальний приклад](img_1_toy_example.png)
На цьому прикладі ми зможемо обговорити, як реалізувати здебільшого незалежні завдання, як отримувати доступ до спільних ресурсів як із завдань, так і з обробників переривань (interrupt service routine, ISR), і - що важливіше - як зберегти код простим. 
Як нам цього досягти? Почнемо з найпростішого підходу, хоч і не найефективнішого.

### 1. Простіше нікуди - опитування (polling) та суперцикл (super loop) 
Ми просто намагаємося прочитати дані, обробити їх, якщо є оновлення, повторити.
Розглянемо приклад коду (скорочений для стислості, [повний код прикладу](https://github.com/sulevsky/multitasking-in-embedded-rust-with-embassy/blob/main/stm32f4xx-hal-examples/examples/polling.rs)).

```rust
const SEND_PERIOD: Duration<u32, 1, 1000> = fugit::MillisDurationU32::millis(1000);

fn main() -> ! {
    info!("POLLING EXAMPLE");
    info!("Starting initialization");
    let dp = stm32f4xx_hal::pac::Peripherals::take().unwrap();
    let mut rcc = dp.RCC.constrain();
    let gpioa = dp.GPIOA.split(&mut rcc);

    info!("Initializing USART2");
    let (mut uart_tx, mut uart_rx) = dp
        .USART2
        .serial::<u8>(
            (gpioa.pa2, gpioa.pa3),
            stm32f4xx_hal::serial::Config::default(),
            &mut rcc,
        )
        .unwrap()
        .split();

    let mut timer = dp.TIM2.counter_ms(&mut rcc);
    timer.start(u32::MAX.micros()).unwrap();

    let mut statistics = Statistics::new();
    let mut send_buffer = Buffer::<128>::new();
    info!("Started data collection");
    let mut next_send = timer.now() + SEND_PERIOD;
    loop {
        match uart_rx.read() {
            Ok(byte) => {
                statistics.update_statistics(byte);
                if send_buffer.is_read_finished() {
                    writeln!(send_buffer, "{}", statistics).unwrap();
                }
            }
            Err(stm32f4xx_hal::nb::Error::Other(error)) => {
                error!("UART error: {:?}", defmt::Debug2Format(&error));
            }
            Err(stm32f4xx_hal::nb::Error::WouldBlock) => {
                // requires blocking to complete
            }
        }

        let now = timer.now();
        if now > next_send {
            if send_buffer.is_read_finished() {
                writeln!(send_buffer, "{}", statistics).unwrap();
            }
            next_send += SEND_PERIOD;
        }
        if !send_buffer.is_read_finished() {
            if let Some(item) = send_buffer.read_next() {
                match uart_tx.write(item) {
                    Ok(_) => send_buffer.mark_byte_as_read(),
                    Err(stm32f4xx_hal::nb::Error::Other(error)) => {
                        error!("UART error: {:?}", defmt::Debug2Format(&error));
                    }
                    Err(stm32f4xx_hal::nb::Error::WouldBlock) => {
                        // requires blocking to complete
                    }
                }
            }
        }
    }
}
```
Ідея циклу опитування здається простою, але з розширенням функціональності починають проявлятися її недоліки. Навіть у цьому простому прикладі ми маємо численні перевірки стану. І весь код тісно пов'язаний (coupled) у головному циклі. 
![Головний цикл відповідає за все](img_2_polling.png)
Головна перевага цього підходу - неблокуюче I/O: якщо лінія передачі чи прийому зайнята, код просто переходить до наступної ітерації замість очікування.
Однак він має кілька ключових недоліків:
1. Низька зв'язність (low cohesion): непов'язані задачі, як-от збір даних і надсилання статистики, знаходяться в одному місці.
2. Часова залежність (temporal coupling): якщо ми додаватимемо все більше завдань, що споживають час CPU, ми ризикуємо тим, що задача надсилання даних не встигне виконатися за відведений їй час. Ще одна часова проблема: якщо цикл не встигає завершити повну ітерацію вчасно, задача збору даних просто пропустить дані.
3. Енергетична неефективність: наш процесор перебуває у циклі активного очікування (busy loop), споживаючи енергію та не виконуючи нічого корисного.

### 2. Блокуюче I/O - просто, але не вирішує наших проблем
Схоже, приклад з опитуванням додав багато випадкової складності - для простої задачі ми отримали купу коду для керування станом. Те, що нам справді потрібно, - це невелика кількість послідовних операцій, що чітко описують проблему, яку ми вирішуємо.
```rust
loop {
    let read_byte = embedded_hal_nb::nb::block!(uart_rx.read()).unwrap();
    statistics.update_statistics(read_byte);
    writeln!(uart_tx, "{}", statistics).unwrap();

    // тут не можна розмістити завдання відправки даних!
}
```
Ці три рядки відповідають операціям зі схеми, що описує задачу прийому даних. Під капотом `embedded_hal_nb::nb::block!` виконує опитування в циклі, до тих пір, поки в UART не з'являться дані. Тому у цьому прикладі ми не можемо інтегрувати в цикл завдання періодичної відправки даних - блокуюче введення-виведення затримує завдання відправки, яке має виконуватися раз на секунду.

З іншого боку, якщо поглянути на завдання відправки даних, проблема, яку ми вирішуємо, вкладається всього у 2 рядки:
```rust
loop {
    delay_ms(1000);
    writeln!(uart_tx, "{}", statistics).unwrap();

    // тут не можна розмістити завдання прийому даних!
}
```
Але тут ми маємо ту саму проблему: `delay_ms(1000)` блокує виконання, тож будь-які дані, надіслані через UART під час цього блокування, будуть втрачені.
Проте я маю аргументи на користь такого коду. Не поспішайте запасатися помідорами — зараз усе поясню!

![Let me explain](img_3_let_me_explain.gif)

Звісно, якщо задачі незалежні, як у нашому прикладі, використання блокуючих операцій - це катастрофа. Але якщо задачі залежать одна від одної (наприклад, простий REPL: прочитати ввід -> розпарсити -> обробити -> вивести), чи є сенс виділяти парсинг в окрему задачу, або робити читання неблокуючим, коли кожен наступний крок логічно залежить від попереднього? У цьому випадку блокуюче I/O здається виправданим: код простіший і зрозуміліший. Здебільшого ми мислимо про виконання коду як послідовність блокуючих операцій. Але що насправді ми цінуємо тут - це не саме блокування, а **послідовний** код: кожен написаний крок чітко залежить від попереднього. Блокування - це просто найпростіший механізм для досягнення цього. Питання в тому, чи можемо ми зберегти послідовний код навіть за наявності кількох задач, не розплачуючись за це завантаженим процесором, - і це саме те, до чого ми прямуємо.

Ось ще один приклад послідовного, але блокуючого коду: чи замислювалися ви коли-небудь, чому кажуть, що функція `sleep()` - це антипатерн? Я маю на увазі не технічні причини, а те, чому про це так часто говорять. Якщо це настільки погано, чому програмісти досі її використовують? Відповідь полягає в тому, що вона проста й зручна. Проста для розуміння, зручна для типових задач на кшталт паузи чи періодичного виконання. Цікаво: а що, якби ми могли використовувати її без недоліків?

Гаразд, перейдемо до більш зрілих підходів і спробуємо вирішити проблему циклу активного очікування.

### 3. Переривання - без блокування і без активного очікування
Щоб позбутися опитування та блокування, перша ідея - це використати переривання: нехай периферія сама сповіщає нас про наявність даних.
Ми розмістимо логіку прийому та відправки всередині обробників переривань (ISR). Ці ISR достатньо легковісні - без важких обчислень, без блокуючих операцій всередині. Хоча в нашому випадку це не проблема, загалом кращою практикою було б зробити ISR максимально короткими і лише сигналізувати про подію через прапорець, залишаючи головному циклу перевірку цього прапорця та обробку події. Це зробило б код головного циклу схожим на приклад з опитуванням, тільки замість стану UART та таймера ми б опитували стан прапорця. Однак для наочності ми залишимо логіку безпосередньо в ISR - це не найкраща практика, але так простіше зрозуміти структуру коду.
[Повний код прикладу](https://github.com/sulevsky/multitasking-in-embedded-rust-with-embassy/blob/main/stm32f4xx-hal-examples/examples/interrupt.rs).
Наш приклад із перериваннями має три ключові секції коду.
1. Функція `main` - відповідає за налаштування застосунку. Оскільки ми вирішили розмістити логіку задач в ISR, головному циклу більше нічого робити, тож він перетворюється на:
```rust
loop {
    asm::wfi();
}
``` 
Ця асемблерна інструкція переводить процесор в режим сну до надходження переривання, тож він не виконує неефективні цикли активного очікування - власне, це і є головною перевагою такого підходу.
Також в `main` ми конфігуруємо USART2 та налаштовуємо обробник приймача UART слухати події `RXNE` (Read Data Register Not Empty). Також ми налаштовуємо таймер. А в контролері переривань ми розмасковуємо `USART2` та `TIM2`, щоб увімкнути відповідні переривання.
2. `TIM2` ISR - реагує на таймер: скидає прапорець переривання таймера та переносить поточну статистику в `SEND_BUFFER`.
3. `USART2` ISR - відповідає за взаємодію з UART як для відправки, так і для прийому. Оскільки ця ISR спрацьовує на дві події, які ми слухаємо (наявність даних в RX - `RXNE`, і TX готовий до відправки - `TXE`, Transmit Data Register Empty), обидва шляхи обробки подій мають знаходитись всередині однієї функції. У частині прийому ми перевіряємо, чи надійшов новий байт (без блокування), оновлюємо статистику і записуємо його в буфер відправки. У частині відправки ми перевіряємо, чи вільний передавач і чи є дані в буфері, після чого надсилаємо один байт.

Здається, підхід з перериваннями вимагає приблизно такого ж обсягу коду для координації, як і підхід із опитуванням. Але тут з'являється додаткова тема для обговорення - спільні ресурси.

![Підхід з перериваннями вимагає керування спільними ресурсами](img_4_interrupt.png)

Візьмемо для прикладу хендлер UART TX типу `stm32f4xx_hal::serial::Tx<stm32f4xx_hal::pac::USART2>` - він має бути спільним для трьох незалежних шляхів виконання, що дуже схоже на те, як три потоки ділять один ресурс. Щоб зробити його доступним для всіх функцій, ми створюємо статичну змінну. Її потрібно ініціалізувати, але сконфігурувати ми можемо лише в `main`, тож ми обгортаємо хендлер в `Option`, ініціалізуючи його як `None` при оголошенні.
Ще один момент: ми не можемо безпечно використовувати цей хендлер між контекстами переривань без гарантії відсутності стану гонок (race conditions), адже цього вимагає компілятор Rust. Тому ми обгортаємо хендлер TX у `Mutex` (щоб гарантувати ексклюзивний доступ) та в `RefCell` (щоб дозволити внутрішню мутабельність).

Підсумовуючи, ось що потрібно для взаємодії з UART TX із обробників переривань у Rust. Зауважте, що фрагменти коду спрощені, а обробка помилок пропущена - інакше допоміжний код просто заховав би суть:

1. Оголошення у статичному блоці
```rust
static UART_TX: Mutex<RefCell<Option<stm32f4xx_hal::serial::Tx<stm32f4xx_hal::pac::USART2>>>> =
    Mutex::new(RefCell::new(None));
```
2. Функція `main` - ініціалізує та оновлює статичну змінну значенням `Some(uart_tx)`.
```rust
let (uart_tx, mut uart_rx) = dp
    .USART2
    .serial::<u8>(
        (gpioa.pa2, gpioa.pa3),
        stm32f4xx_hal::serial::Config::default(),
        &mut rcc,
    )
    .unwrap()
    .split();

cortex_m::interrupt::free(|cs| {
    UART_TX.borrow(cs).replace(Some(uart_tx));
});
```
3. ISR `TIM2` - вмикає відстеження подій `TXE` після таймауту
```rust
cortex_m::interrupt::free(|cs| {
    UART_TX.borrow(cs).borrow_mut().as_mut().unwrap().listen();
});
```
4. ISR `USART2`
   - вмикає відстеження подій `TXE`, коли статистику оновлено
```rust
cortex_m::interrupt::free(|cs| {
    UART_TX.borrow(cs).borrow_mut().as_mut().unwrap().listen();
});
```
   - записує в UART, якщо в буфері є дані для надсилання
```rust
cortex_m::interrupt::free(|cs| {
    UART_TX.borrow(cs).borrow_mut().as_mut().unwrap().write(byte).unwrap();
});
```
   - вимикає відстеження подій `TXE`, коли буфер порожній
```rust
cortex_m::interrupt::free(|cs| {
    UART_TX.borrow(cs).borrow_mut().as_mut().unwrap().unlisten();
});
```

Це доволі складне налаштування для хендлера UART TX, і подібне налаштування нам доведеться робити для всіх спільних ресурсів:
- UART_RX
- UART_TX
- STATISTICS
- SEND_TIMER
- SEND_BUFFER
Це виглядає як купа підготовчої роботи. І якщо спробувати знайти в такому коді бізнес-логіку (ті самі п'ять рядків із блокувального прикладу), зробити це буде непросто.

Підсумуємо переваги та недоліки підходу з перериваннями.
Мінуси:
- Складне налаштування
- Бізнес-логіка розкидана по багатьох місцях
- Потрібна синхронізація
Плюси:
- Без блокування, задачі незалежні
- Вища енергоефективність
Енергоефективність далася нам ціною простоти. І ми навіть не отримали повністю ту ефективність, за яку заплатили: ISR `USART2` спрацьовує на кожен отриманий байт. Якщо надходить великий потік байтів, це спричиняє багато викликів ISR, а кожен із них вимагає перемикання контексту, що споживає енергію. Частина щойно здобутого виграшу в ефективності одразу ж витрачається на накладні витрати від переривань. Подивимось, чи зможе DMA це виправити.

### 4. Переривання з DMA
Тепер перейдемо від простої обробки переривань до DMA: якщо у попередньому прикладі переривання відповідало за переміщення кожного байта з UART у пам'ять, то тут цю роботу бере на себе DMA. Конфігурація таймера не змінилась, тож я не буду її повторювати. Нове тут - це налаштування UART і додана конфігурація DMA.

[Повний код прикладу](https://github.com/sulevsky/multitasking-in-embedded-rust-with-embassy/blob/main/stm32f4xx-hal-examples/examples/dma.rs).

DMA виступає посередником між UART і пам'яттю: він зчитує вхідні байти і записує їх у буфер. Коли буфер заповнюється, спрацьовує переривання і виконується ISR `DMA1_STREAM5`. Ця ISR робить дві речі:
1. Керує буферами DMA - перемикається на інший буфер (це патерн ping-pong), зчитує щойно заповнений, очищає його і зберігає в статичній змінній для наступного перемикання.
2. Оновлює статистику на основі отриманими даних і записує результат у буфер надсилання

ISR `DMA1_STREAM5` викликається лише тоді, коли буфер повністю заповнений. Але якщо UART отримує порцію байтів, яка не заповнює буфер повністю, ISR `DMA1_STREAM5` не спрацює, і дані залишаться необробленими. Щоб врахувати цей випадок, ми повертаємо нашого доброго друга - ISR `USART2` - але цього разу він не спрацьовує на кожен байт. Натомість він спрацьовує на переривання `IDLE`, яке виникає, коли UART "мовчить" протягом тривалості одного фрейму, сигналізуючи, що відправник зробив паузу. Всередині ISR `USART2` ми виконуємо майже ту саму роботу, що й в ISR `DMA1_STREAM5`, за винятком того, що читаємо лише ту частину буфера, яка дійсно була заповнена.
Так само, як і в підході лише з перериваннями, DMA додає свій власний набір спільних ресурсів, які потрібно координувати.
![Підхід з DMA вимагає керування спільними ресурсами](img_5_dma.png)
Розглянемо цей підхід. Він доволі ефективний: процесор нічого не робить, коли робити нічого, а DMA бере на себе роботу з передачі даних, ще більше розвантажуючи CPU. Тепер ISR спрацьовує лише коли буфер заповнений або передача завершилася, а не на кожен байт.
Фух! Звучить непогано. Маємо чим пишатися.
Але які тут плюси і мінуси?
Мінуси:
- Конфігурація стала ще складнішою
- Бізнес-логіка розкидана ще по більшій кількості місць
- Більше спільних ресурсів вимагають синхронізації

Плюси:
- Без блокування, задачі залишаються незалежними
- Ще вища енергоефективність порівняно з підходом лише на перериваннях

Тут варто зробити паузу. Ми прийшли до конфігурації, яка є оптимальною з точки зору ефективності, але нам довелося пройти довгий шлях, щоб опинитись тут. І в цьому вся проблема: розробники звертаються до оптимального підходу лише тоді, коли це легко, або коли вимоги не залишають іншого вибору. З цієї ж причини ми так часто бачимо функцію `sleep()` в коді, хоча всі погоджуються, що це не найкраща практика, це просто легко.

## Поєднання простоти та ефективності з Embassy
Простота послідовного блокуючого коду. Ефективність DMA і переривань. Чи є спосіб отримати і те, й інше?
На допомогу приходить Embassy - фреймворк для розробки вбудованих застосунків на Rust. Особисто я почав дослуджувати його через асинхронний підхід до багатозадачності, але чим глибше я занурювався, тим більше його функціонал змушував мене щиро захоплюватися фреймворком. Розглянемо деякі фічі на нашому прикладі.
### Async/Await
Робота з I/O вимагала від нас складного керування станом. Тепер ми можемо передати цю відповідальність спеціальному компоненту фреймворку Embassy - executor'у. Коли executor натрапляє на блокуючу операцію всередині асинхронної функції, він може переключитися на інші задачі або перевести процесор в режим сну. Проте для розробника все це абстраговано - код виглядає як простий виклик функції.
Наприклад, у цьому фрагменті ми зчитуємо дані з UART у буфер пам'яті:
```rust
let mut buffer = [0u8; 512];
let num_bytes_read = uart_rx.read_until_idle(&mut buffer).await.unwrap();    
```

### Задачі (Tasks)
Як і в багатьох RTOS, виконання в Embassy організоване у вигляді задач (tasks), які є просто async-функціями з макросом `#[embassy_executor::task]`.
```rust
#[embassy_executor::task]
async fn task_name() {
    // task's code
}
```
Ми визначаємо задачі Embassy як асинхронні функції. Чим хороші ці функції? По-перше, є чіткий поділ відповідальності: задачі ізольовані, а код не переплетений між собою, на відміну від прикладів з опитуванням і перериваннями. По-друге, хендлери периферії передаються як параметри, тож нам більше не потрібно обгортати хендлер UART RX в `Mutex`, `RefCell` та `Option` - ми обгортаємо лише те, що дійсно є спільним між задачами, а це в нашому випадку - лише агрегована статистика та хендлери UART TX.
![Задачі Embassy](img_5_embassy.png)
Для нашого прикладу буде 3 задачі:
```rust
#[embassy_executor::task]
async fn collect_statistics(mut uart_rx: UartRx<'static, Async>) {
    let mut buffer = [0u8; 512];
    loop {
        let num_bytes_read = uart_rx.read_until_idle(&mut buffer).await.unwrap();
        for i in 0..num_bytes_read {
            STATISTICS.lock().await.update_statistics(buffer[i]);
        }
        STATISTICS_UPDATED.signal(());
        buffer.fill(0);
    }
}

#[embassy_executor::task]
async fn send_statistics_on_update() {
    loop {
        STATISTICS_UPDATED.wait().await;
        send_statistics().await;
    }
}

#[embassy_executor::task]
async fn send_statistics_periodically() {
    loop {
        Timer::after(SEND_PERIOD).await;
        send_statistics().await;
    }
}
```
### Функція main
Функція `main` змінилась: тепер вона асинхронна і позначена макросом `#[embassy_executor::main]`, тож executor Embassy бере на себе запуск і керування рантаймом. `main` також приймає `Spawner` як параметр, що дозволяє нам запускати нові задачі. 
У тілі функції ми конфігуруємо периферію та запускаємо задачі - і, власне, це все: ініціалізація застосунку з єдиною відповідальністю.
```rust
static STATISTICS: Mutex<CriticalSectionRawMutex, Statistics> = Mutex::new(Statistics::new());
static UART_TX: Mutex<CriticalSectionRawMutex, Option<UartTx<'static, Async>>> = Mutex::new(None);
static STATISTICS_UPDATED: Signal<CriticalSectionRawMutex, ()> = Signal::new();

#[embassy_executor::main]
async fn main(spawner: Spawner) {
    let p = embassy_stm32::init(Default::default());
    let (uart_tx, uart_rx) = embassy_stm32::usart::Uart::new(
        p.USART2,
        p.PA3,
        p.PA2,
        p.DMA1_CH6,
        p.DMA1_CH5,
        Irqs,
        embassy_stm32::usart::Config::default(),
    )
    .unwrap()
    .split();
    UART_TX.lock().await.replace(uart_tx);
    spawner.spawn(collect_statistics(uart_rx).unwrap());
    spawner.spawn(send_statistics_periodically().unwrap());
    spawner.spawn(send_statistics_on_update().unwrap());
}
```
Мені подобалося, як інструкція `WFI` в головному циклі утримувала процесор від марної роботи. Але ще більше подобається, що тепер у `main` взагалі немає циклу - функція просто виконує свою роботу і завершується. Втім, цикл нікуди не зник - він просто тепер захований всередині executor'а.

### DMA
У попередніх прикладах ми бачили, що конфігурація DMA складна, і саме це відлякує розробників від її використання.
З Embassy увімкнення DMA для UART - це лише два додаткові параметри:
```rust
let (uart_tx, uart_rx) = embassy_stm32::usart::Uart::new(
    p.USART2,
    p.PA3,
    p.PA2,
    p.DMA1_CH6, // <--- DMA configuration for the UART TX
    p.DMA1_CH5, // <--- DMA configuration for the UART RX
    Irqs,
    embassy_stm32::usart::Config::default(),
)
.unwrap()
.split();
```
І конфігурація переривань виконується за допомогою макросу `bind_interrupts!`, який перевіряє прив'язки на етапі компіляції:
```rust
bind_interrupts!(
    struct Irqs {
        USART2 => usart::InterruptHandler<peripherals::USART2>;
        DMA1_STREAM5 => dma::InterruptHandler<peripherals::DMA1_CH5>;
        DMA1_STREAM6 => dma::InterruptHandler<peripherals::DMA1_CH6>;
    }
);
```
Якщо ж я забуду прив'язати `DMA1_STREAM5 => dma::InterruptHandler<peripherals::DMA1_CH5>`, то отримаю помилку компіляції замість збою у готовому продукті.
```
the trait bound `Irqs: Binding<DMA1_STREAM5, InterruptHandler<DMA1_CH5>>` is not satisfied
```
Це величезна перевага Rust в embedded-розробці - подібні баги виявляються до релізу. [Більше про те, як Rust допомагає виявляти дефекти на ранніх етапах](https://dou.ua/forums/topic/60424/)
Тож із Embassy використання DMA є водночас і простим, і безпечним - це сильний аргумент на користь фреймворку. Найкраща практика стає тією, якій легко слідувати.
Просто наведу цитату з [документації Embassy](https://embassy.dev/book/#_what_is_dma:~:text=However%2C%20because%20DMA%20is%20more%20complex%20to%20set%2Dup%2C%20it%20is%20less%20widely%20used%20in%20the%20embedded%20community.%20Embassy%20aims%20to%20change%20that%20by%20making%20DMA%20the%20first%20choice%20rather%20than%20the%20last.):
> Оскільки DMA складніше налаштувати, воно менш поширене в embedded-спільноті. Embassy прагне змінити це, зробивши DMA першим вибором, а не останнім.

З огляду на це, зберемо все разом у повне рішення з використанням Embassy
[Повний код прикладу](https://github.com/sulevsky/multitasking-in-embedded-rust-with-embassy/blob/main/embassy-examples/examples/embassy.rs).

## Підсумок
- Ми взяли просту та поширену задачу у розробці вбудованих систем - зчитати дані з UART, обробити їх та періодично відправляти результати - і вирішили її п'ятьма різними способами, щоб дослідити компроміс між простотою та ефективністю.
- Опитування (polling) найпростіше реалізувати, але воно переплітає непов'язану бізнес-логіку разом і марнує ресурси процесора в циклі опитування
- Блокуючий, послідовний код ще простіший і відповідає нашому природному мисленню про задачу, але він підходить лише для невеликої кількості задач з дуже м'якими вимогами до таймінгів
- Переривання прибирають цикл опитування та блокування, але платою за це є розпорошена по ISR логіка та ручна синхронізація для кожного спільного ресурсу
- Додавання DMA підвищує ефективність за рахунок зменшення кількості викликів ISR, але ціною ще більшої складності налаштування, через що цей оптимальніший підхід рідше використовують
- Асинхронність (async/await) в Embassy усуває цей компроміс: задачі виглядають як простий, послідовний код, тоді як executor бере на себе планування та переведення процесора в режим сну «під капотом». Виявляється, ми можемо отримати і те, і інше.
